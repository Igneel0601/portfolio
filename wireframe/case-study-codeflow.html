02# tl;dr

A web app where you type "build me a pricing page with three tiers" into a chat, an agent spins up an isolated E2B sandbox, scaffolds a Next.js project, writes the files, and streams the live preview back to you in under a minute. Built solo over 9 weekends.

  • ›What: v0 / bolt-style builder. Chat in, deploy-ready React out.
  • ›Hard part: orchestrating long-running sandbox jobs without blocking the chat UI.
  • ›Why it matters: validated that single-dev AI tooling can be production-grade.

03# the problem

Existing builders (v0, bolt.new, lovable) are great — but they're closed-source and opinionated about hosting, framework, and provider. I wanted to know if a single engineer could build a credible alternative on consumer-grade infra, learn the agent-orchestration patterns, and end up with something I'd actually use for client kickoff prototypes. Time-to-prototype was the metric.

06# architecture

The whole thing is three async loops glued together: chat (instant), agent (long-running, lives in Inngest), and sandbox (lives in E2B). The trick was keeping the chat responsive while the agent burns 30+ seconds writing files.

07# key decisions

01

Inngestvs.custom queue + redis

I needed durable, retryable steps that survive cold starts. Rolling BullMQ on a $5 Redis was 3 weekends I didn't have. Inngest's step.run API made the agent loop feel like normal imperative code while quietly being a state machine.

02

E2B sandboxesvs.webcontainers

WebContainers are magical but iframe-bound and quota-limited. E2B gives a real Linux box per session — I can run pnpm install, spawn next dev, and tail logs. Cost ~3¢/session in practice.

03

tRPC + Server Actionsvs.REST

End-to-end types meant I caught two whole categories of bugs at compile time. Server Actions for mutations, tRPC subscriptions for the stream of file-write events from the agent.

04

gpt-4o-mini default, Sonnet fallback

Mini handles 80% of the file-writing fine at 1/10th the cost. I route to Sonnet automatically when the planning step's confidence score drops below 0.6 — caught in provider.ts:routePlan.

09# deep dive · the hard part

Keeping the chat responsive while the agent writes 40 files in 30 seconds means you can't just await the LLM and call it a day. Each file-write becomes an Inngest step, and the client subscribes to a tRPC onFileWrite stream that fans out from the same job ID.

agent.ts typescript 
export const runAgent = inngest.createFunction(
  { id: "run-agent" },
  { event: "agent/prompt.submitted" },
  async ({ event, step }) => {
    const plan = await step.run("plan", () => planFiles(event.data.prompt));

    for (const file of plan.files) {
      // each file is its own retryable step
      await step.run(`write:${file.path}`, async () => {
        const contents = await writeFile(file, plan.context);
        await sandbox.write(file.path, contents);
        await pubsub.publish(event.data.jobId, { file, contents });
      });
    }

    return { status: "done", files: plan.files.length };
  }
);
snippet 01 · the agent loop. every file is its own resumable unit.

The aha moment: once each file is a step, retries are free, partial-progress on cold start is free, and the UI just needs to listen for the published events. The chat input never blocks.

11# what I'd do differently

  • Stream the plan, not the prompt. I spent two weekends rebuilding chat streaming when a plan-first UX would have made waits feel intentional, not laggy.
  • E2B has cold-start tax. Pre-warming a pool of 3 sandboxes shaved 6 seconds off median TTI but I only added it in week 7.
  • Prisma migrations in a sandbox are awkward. Next time I'd ship with Drizzle to avoid the codegen step inside the user's environment.
  • Don't ship without auth. I added Clerk last; bolting it on touched 40% of the routes. Should have been step 2.
